- (decision) Single Piranha CMS installation (one deployment, one database) using Piranha's native multi-site feature to serve Site A (tbtruonghoc) and Site B (trongdoitam.net) as two Site records, with Site C to join later as a third. Rationale: SEO ranking is per-domain (sitemap/robots/Search Console already separate per FR-4) and is unaffected by shared-vs-separate CMS backend; the commonly-owned-domain link-scheme risk (addendum.md) stems from WHOIS/registrant visibility, not CMS topology, and is already mitigated by FR-5's editorial-only cross-linking. Self-hosted by Phuoc, who is comfortable operating it and not risk-averse to shared-instance blast radius. Binds: all. Prevents: divergent hosting/ops setups per site, duplicated media libraries, duplicated admin/user management.
- (constraint) Piranha CMS multi-site is single-tenant under the hood: confirmed via piranhacms.org/docs (how-to-use-multitenancy) and GitHub issue #982 that all sites in one installation share one media library and all CMS users have access to all sites/resources — there is no per-site content-type restriction or per-site user restriction. Acceptable now since Phuoc is sole content admin; revisit if a second editor needing Site-B-only access is ever added (Deferred).
- (decision) Design paradigm: Archive+Post for anything list/taxonomy-shaped (each danh muc category = an Archive page hosting Posts as products; blog FR-7/FR-14 reuses the same Archive+Post mechanism) leveraging Piranha's native pagination/category/tag support; standalone Page for anything that stands alone (homepage, aggregate Danh muc san pham hub page, landing pages FR-12, craftsman story page FR-10) since these must NOT paginate/list and landing pages must stay excluded from nav/archive listings. Confirmed by Phuoc. Binds: FR-6, FR-7, FR-9, FR-10, FR-12, FR-14. Prevents: one site building products as free-standing Pages while the other uses Archive+Post, breaking shared templating/URL conventions and duplicating pagination logic.
- (decision) Lead capture (FR-3 general contact, FR-8 survey request): custom EF Core table(s) in the shared Piranha database (not Piranha's built-in Comment/PostComment model, which is a fixed-schema public blog-comment feature tied only to Posts, with no phone/address/product fields and a real privacy risk of publicly displaying customer contact info if approved) storing all submitted fields with a form-type discriminator so both forms share one storage mechanism instead of each site inventing its own. A custom Piranha Manager extension module (confirmed supported via Manager Extensions docs: menu integration, custom resources, Vue components) adds a 'Danh sach khach de lai thong tin' admin section replacing Phuoc's current pen-and-paper tracking, with detail view per submission. Email notification fires on every new submission. Binds: FR-3, FR-8. Prevents: forms silently dropping data into unretrievable email-only channels, divergent per-form/per-site storage schemes, customer PII (phone/address) leaking into a public comment-approval flow.
- (decision) 301/302 redirects (both same-domain Site A URL changes and cross-domain Site A -> Site B for legacy trong content) use Piranha's native Alias feature (IApi.Aliases, AliasRouter middleware), not custom middleware. Verified via source (core/Piranha/Models/Alias.cs): Alias.RedirectUrl is an unconstrained string (no same-domain validation), so it accepts absolute external URLs -- confirmed workable for the cross-domain case. Each alias is scoped by SiteId to the site where the OLD url lived (Site A for both same-domain and the cross-domain-to-Site-B redirects, since legacy URLs are all currently under tbtruonghoc.com). Binds: content-migration/redirect plan (addendum.md). Prevents: inventing a custom redirect table/middleware that duplicates a native, already-available mechanism, and inconsistent redirect handling between the same-domain and cross-domain cases.
- (version) Stack pinned per Phuoc's choice + web verification (Sept 2026): .NET 8 (LTS) on CentOS Stream 9, self-hosted. Piranha CMS 12.2.0 (latest stable, verified on GitHub releases, cross-compiles for .NET 8/9 -- .NET 8 chosen for LTS stability over .NET 9 STS). Project scaffolded from the official 'piranha.mvc' template (Piranha.Templates 12.0.0, installed via 'dotnet new install Piranha.Templates' then 'dotnet new piranha.mvc -d MySql'). Database: MySQL via Piranha.Data.EF.MySql 12.0.0 (Piranha's officially integrated MySQL package, built on Pomelo.EntityFrameworkCore.MySql) -- one shared MySQL database for both Site A and Site B site records (per the single-Piranha-instance decision).
- (decision) Consistency conventions (routine, low-ambiguity, settled without further elicitation): (1) Pricing display -- Product Post Type (drums, bathtubs, most Site A categories) defaults to no visible price field, CTA is contact-for-quote; Landing Page Type (FR-12/13, Site B only) carries its own repeatable variant+price region, kept separate from the Product Post Type so organic product pages never accidentally expose a price field. (2) Cross-site linking (FR-5) is a plain hyperlink placed manually by the content editor inside a Post/Page rich-text block -- no dedicated link-block component, no automation, so it can never become a sitewide link block by accident. (3) Media storage: local filesystem on the CentOS host (Piranha's default local storage manager), shared across both sites per the single-instance decision -- no cloud/object storage added since self-hosted with no stated redundancy requirement. (4) Per-site Analytics/Search Console (FR-4): GA4 measurement ID and any per-site tracking config stored as a field on each Piranha Site's settings/site type, injected into that site's shared layout -- never hardcoded, so each site's tag is swappable without a deploy. Binds: FR-4, FR-5, FR-12, FR-13.
- (decision) Backup/DR (reviewer-flagged gap: AD-1's single shared MySQL database is a new single point of failure for both sites at once): automated daily mysqldump backup of the shared MySQL database, retained 14 days, stored on the CentOS host. Phuoc has no existing backup process to preserve; this default accepted as-is. Binds: all (both sites depend on the one database).
- (decision) AD-5 revised per Phuoc's direct correction: pricing is NOT landing-page-exclusive. The Product Post Type also carries an optional price field, flexible format (exact value, a range, or 'tu X' starting-price), editable in CMS same as any other field -- editor leaves it blank for pure contact-for-quote items. Whether or not a price is shown, the 'Lien he bao gia' (contact-for-quote) CTA is always present alongside it -- price display and contact-for-quote are not mutually exclusive. The Landing Page Type keeps its own separate repeatable variant+price region (structured multi-variant pricing, e.g. thung ruou's 4 variants), which is a distinct use case (paid-campaign, multiple SKUs at once) from the single flexible price field on a regular Product Post. Supersedes the prior 'Product Post Type carries no price field' rule.
- (decision) Reviewer-driven tightenings applied at Finalize (rubric walker + web-verification + adversarial subagent reviews, all three logged under reviews/): (1) AD-1 Rule extended -- Site records (hostnames, IsDefault) are created ONCE by whoever runs initial project scaffold/setup, not re-derived per feature builder; a second Piranha instance must never be spun up 'for Site B' even via the official dotnet-new quickstart. (2) AD-3 Rule tightened -- FormSubmission canonical schema fixed explicitly: id, site_id, form_type, name, phone, product_of_interest, message, location_address (nullable, FR-8 only), is_outside_service_area (bool, nullable), created_at -- one shared table, fixed nullable columns, not a free-form JSON blob and not per-form-type subtables, so FR-3 and FR-8 builders cannot each invent a different shape. (3) AD-4 Rule tightened -- cross-domain aliases (Site A legacy trong URLs -> Site B) are only created after Site B's final URL/slug structure is frozen (not before), to avoid dead redirects if Site B slugs change after aliases are set. (4) AD-2 Rule tightened -- the aggregate 'Danh muc san pham' hub page sources its category list dynamically by querying the site's Archive pages at render time, never a hand-curated/hardcoded link list, matching the UX spec's 'CMS-flexible list, placeholder tile for future categories.' (5) Consistency Conventions: added an FR-2 row (phone/Zalo/Maps contact details also live on the same per-Site settings type as FR-4's GA4 config, never hardcoded per-view) and named that shared settings content type explicitly ('SiteSettings' SiteType, one per Piranha Site) since FR-2 and FR-4 both depend on it. (6) Stack: MySQL pinned to 9.7 LTS (verified: MySQL 8.0 reached EOL 2026-04-30; 8.4 and 9.7 are the current LTS lines, 9.7 released April 2026 chosen as the newer LTS). (7) .NET 8 stack pin's rationale corrected -- not chosen for 'LTS vs 9 STS' (both .NET 8 and 9 reach End of Support on the same date, 2026-11-10, per Microsoft devblog); .NET 8 is the only option because Piranha 12.2.0 does not yet cross-compile for .NET 10 (the actual current LTS, supported to Nov 2028) -- flagged in Deferred as a near-term forced upgrade once Piranha adds net10.0 support.
