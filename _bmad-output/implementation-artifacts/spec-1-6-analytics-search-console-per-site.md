## Intent

**Problem:** Site A and Site B currently have no way to report to their own GA4 property or verify themselves independently in Search Console — there is no field or rendering for either, and no code confirms the per-site `sitemap.xml` Search Console needs actually exists.

**Approach:** Extend the existing per-site `SiteSettings` SiteType (`src/TbTruongHoc.Web/Models/SiteSettings.cs`, added in Story 1.3) with a GA4 measurement ID field and a Search Console verification-value field — same singleton-per-`Site`, editable in Piranha Manager, no code deploy needed to change either value. Render them from a new `_Analytics.cshtml` head partial (gtag.js snippet + `google-site-verification` meta tag), included in `_Layout.cshtml`'s `<head>` so it applies to every page on both sites, using the same `WebApp.Site.GetContentAsync<SiteSettings>()` pattern `_ContactBlock.cshtml` already uses. Both the script and the meta tag render only when their respective field is non-empty (fields are expected to stay empty in dev/pre-launch). Confirm Piranha's built-in `SitemapMiddleware` (already wired in by `UsePiranha(...)`, already covered by `HostnameResolutionTests.cs`'s `/sitemap.xml` check) serves an independently-scoped sitemap per resolved site — this story adds no new sitemap code unless investigation during implementation finds it does not actually scope per site.

</frozen-after-approval>

## Implementation Notes

- Added `Ga4MeasurementId` and `SearchConsoleVerification` `StringField`s to the existing `SiteSettings` SiteType (`src/TbTruongHoc.Web/Models/SiteSettings.cs`) — auto-discovered by the existing `ContentTypeBuilder` call, no migration needed (Piranha content types are region-based, not EF-schema-based).
- New `src/TbTruongHoc.Web/Views/Shared/_Analytics.cshtml` partial reads both fields via `WebApp.Site.GetContentAsync<SiteSettings>()` (same pattern as `_ContactBlock.cshtml`) and renders a `google-site-verification` meta tag plus a standard gtag.js snippet, each gated independently on its own field being set. Included once in `_Layout.cshtml`'s `<head>`, before `@RenderSection("head", ...)`, so it applies to every page on both sites.
- **Format validation added (not originally called out in the Intent, but required by the same defense-in-depth convention Story 1.3 already established for Zalo/Maps URLs):** because the GA4 ID is embedded directly into an inline `<script>` block and both values are embedded into HTML attributes, a Manager-entered value containing a quote or angle bracket could otherwise break out of that context. Added `IsValidGa4MeasurementId` (`^G-[A-Za-z0-9]+$`) and `IsValidSearchConsoleVerification` (`^[A-Za-z0-9_-]+$`) to `SiteSettingsValidation.cs`; `_Analytics.cshtml` treats a value failing its check as unset (omits the tag/script, same as an empty field), and `Program.cs`'s existing `App.Hooks.SiteContent.RegisterOnBeforeSave` hook (previously only guarding Zalo/Maps) now also rejects an invalid GA4 ID or verification value at save time with a `ValidationException`, evicting the site-content cache the same way it already did for Zalo/Maps.
- **Sitemap: confirmed, no new code.** Piranha.AspNetCore 12.0.0 ships `SitemapMiddleware`, wired in automatically by `UsePiranha(...)` and already resolving the sitemap from the current request's resolved `Site` (the same hostname-based resolution `_ContactBlock.cshtml`/`_Analytics.cshtml` rely on). Added `Sitemap_Is_Scoped_To_Each_Sites_Own_Published_Pages` to the new test file to prove this directly (two sites, two distinct published-page slugs, each site's `/sitemap.xml` contains only its own slug) — this closes the gap `HostnameResolutionTests.cs`'s existing sitemap check left open (it only asserted the endpoint doesn't error, not that it scopes correctly, since no pages existed yet when that story was written).
- New `tests/TbTruongHoc.Web.Tests/AnalyticsSearchConsoleTests.cs` (5 tests, mirrors `SiteSettingsTests.cs`'s snapshot/restore pattern against the real MariaDB-backed `IApi`): cross-site isolation, both fields omitted when unset, save-time rejection of an invalid GA4 ID/verification value (each with an injection-shaped payload attempting to break out of the `<script>`/attribute context), and the sitemap-scoping test above.
- `dotnet build TbTruongHoc.sln` — 0 errors (same pre-existing Piranha 12.0.0 NuGet advisory warnings prior stories already noted). `dotnet test TbTruongHoc.sln` against real MariaDB (`docker compose up -d mariadb`, `ConnectionStrings__piranha` exported per README) — **46/46 passed** (41 pre-existing + 5 new), no regressions.
- Manual Manager click-through (confirming the new fields appear in Site Settings' edit UI, and that a real page's rendered `<head>` shows the script/meta tag once values are entered) was not performed this session, same constraint Story 1.5 noted — no fresh console-printed admin credentials were available. Everything short of that visual check is covered by the tests above (which call the real save path and the real HTTP-rendered page, just not through a logged-in Manager UI). The user should do one manual check with their own Manager credentials.
- After the review's patch round (3 findings routed to `patch`; see `## Review Triage Log`): relaxed `SearchConsoleVerificationPattern` to also allow `.`/`+`/`=` (real Search Console tokens can contain these; Razor's default HTML-encoding is the actual attribute-injection defense, not this regex), added a `{4,}` minimum length to `Ga4MeasurementIdPattern` to catch an obviously truncated paste, and updated `SiteSettingsSeed.cs`'s stale doc comment to list the two new fields alongside Phone/ZaloUrl/Address/MapsUrl. Re-verified: `dotnet build` — 0 errors; `dotnet test` against real MariaDB — **46/46 passed**, no regressions (existing GA4/verification tests still pass unchanged under the relaxed/tightened regexes since their fixture values were already within both new bounds).

## Review Triage Log

- **[low, rejected]** (blind-hunter) `Program.cs`'s `RegisterOnBeforeSave` hook only surfaces one validation error at a time via a nested ternary (Zalo → Maps → GA4 → verification) — a save with two invalid fields at once only reports the first. Verified: the ternary chain is exactly as described, and this limitation already existed for Zalo/Maps before this story; this story only extended the same pattern to two more fields rather than introducing it. Rare in practice (Manager users typically fix one field at a time) and the fix (aggregating multiple errors into one message) is more than a direct correction — rejected per the low-finding rule.
- **[low, rejected]** (blind-hunter) No test seeds an already-invalid GA4 ID/verification value (bypassing the save-time hook) and asserts `_Analytics.cshtml` still treats it as unset at render time, per its own header-comment claim. Verified: true, all 5 new tests only cover values that are either valid-and-persisted or rejected outright by the hook. This path is only reachable today via a direct DB write bypassing Piranha's content-save API entirely (the hook always runs on every Manager/API save) — matches the same standard already applied to Phone/Zalo/Maps in `SiteSettingsTests.cs`, none of which test this exact scenario either. Rejected: fix requires reaching into Piranha's internal content-persistence layer to fabricate the stale-invalid state, which is more than a simple correction.
- **[patch]** (blind-hunter) `Ga4MeasurementIdPattern` had no length bound, so an obviously truncated paste like `G-X` would validate and be saved/rendered, silently breaking analytics until noticed on the GA4 dashboard. Fixed: added a `{4,}` minimum to `SiteSettingsValidation.cs`'s `Ga4MeasurementIdPattern`.
- **[medium, deferred]** (blind-hunter) `_Analytics.cshtml` renders the gtag.js snippet with no environment gating — a real production GA4 ID pasted into a non-production environment's Manager (dev/staging) would fire live pageview events into the production property with no code-level guard. Verified: no `ASPNETCORE_ENVIRONMENT` check exists anywhere in the partial. Real but requires a product decision (code gate vs. operational rule) outside this story's frozen Intent — deferred to `deferred-work.md`.
- **[low, rejected]** (blind-hunter) The spec's own Implementation Notes already flag that the manual Manager UI click-through was skipped this session (no fresh admin credentials available) — reviewer noted this should "stay open," but it is already recorded as an open item for the user; no additional code action needed.
- **[low, patch]** (blind-hunter) `SiteSettingsSeed.cs`'s doc comment (line 13) still listed only Phone/ZaloUrl/Address/MapsUrl as the fields its get-or-create seed protects from being clobbered on restart, not mentioning the two new fields it now also covers. Fixed: updated the comment to list all six fields.
- **[low, deferred]** (blind-hunter) No explicit product decision is recorded on cookie-consent/IP-anonymization/Consent Mode for the unconditionally-firing gtag.js script. No PRD/epic-context requirement mentions this for these Vietnamese SMB sites, so it may be a non-issue, but it wasn't a deliberate call either — deferred to `deferred-work.md` for an explicit yes/no before launch.
- **[patch]** (blind-hunter) `SearchConsoleVerificationPattern` (`^[A-Za-z0-9_-]+$`) was admitted (in its own comment) to be a guess at Google's token grammar, risking rejection of a legitimate real-world verification value containing e.g. `.` or `+` — with no compensating security benefit since Razor's default HTML-encoding already neutralizes any attribute-breakout attempt regardless of this regex. Fixed: relaxed the pattern to `^[A-Za-z0-9_.=+-]+$`, still excluding whitespace/quotes/angle-brackets.
